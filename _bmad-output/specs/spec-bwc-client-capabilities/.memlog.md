- (capability) CAP-1 register with optional capabilities bitmask via 4/6/7-field add-client CSV (decimal or hex), single-byte id response unchanged; omitting or zero = legacy behaviour, byte-identical to pre-release server on 9002
- (capability) CAP-2 WIDE_COORDS (bit 0x01): x/y decoded as int16 LE, region-relative, scaled to registered screen size, may be slightly negative or oversized at edges/wrap seam, clip to viewport; motion advances by small pixel deltas, not 8px quantised jumps
- (capability) CAP-3 ROTATION (bit 0x02): angle uint16 LE (bits/65535*2pi rad, CCW from +Y) + omega int16 LE (bits/256 rad/s, positive CCW) appended after x/y per shape; all copies of a bodyId carry identical angle/omega; local interpolation via omega allowed with resync each packet; shapes render rotated and visibly spin, including from birth (anti-drift spawning)
- (constraint) Capability bit values are fixed shared constants: 0x01 WIDE_COORDS, 0x02 ROTATION; unknown bits must be ignored; server never sends data for unrequested capabilities
- (constraint) Port split 9002 raw / 9003 2-byte LE length prefix unchanged and orthogonal to capabilities; REST POST /client accepts same 4/6/7-field body, returns 1-byte id with HTTP 201
- (constraint) World payload header unchanged: stepNumber u8, appStatus u8, shapeCount u8 (max 240); per-shape size depends on requested caps: 3B legacy, 5B wide, 9B wide+rotation
- (constraint) Without WIDE_COORDS x/y are uint8 read unsigned; values >=128 near edges possible and treated as-is
- (constraint) Client requests only what it will decode; rule bends parser design toward capability-gated decode paths
- (question) Does the Amiga client work specced in spec-amiga-bounce-world-client switch from version>=3 inference to the capabilities bitmask, or does that older spec stay authoritative for its delivery?
