- (direction) Source: backlog/amiga-bounce-world-client.md plus user clarification in chat; user uses bounce/bouncy interchangeably, repo is bounce-world-client-nio
- (decision) Add a native Amiga target to bounce-world-client-nio rendering shapes as vector graphics on a fullscreen custom screen; first graphical client among text-based targets
- (decision) No server or protocol change: server accepts any client-declared resolution and maps its 40.0x24.0 float world space into that resolution as integers; existing per-platform REG_SCREEN_WIDTH/HEIGHT and REG_WORLD_WIDTH/HEIGHT registration constants already carry this
- (decision) Client embeds the known shape table (shapes[19]) like BBC/other targets and hard-codes rendering from shape ids; server always sends same shape info
- (decision) Display: fullscreen custom lowres screen (320x256 PAL / 320x200 NTSC) with double buffering, chosen over Workbench window for KS1.3 unexpanded compatibility
- (decision) Rendering: filled polygons via graphics.library area functions (AreaDraw/AreaEnd), standard on all Kickstarts
- (decision) Sound is in scope: collision/event sound effects equivalent to other targets using KS1.3-available audio APIs
- (constraint) Must run on Workbench/Kickstart 1.3 up and all machine types (A500/A1200 class); standard Amiga OS libraries only (intuition/graphics/dos), no third-party graphics libs
- (constraint) Shapes are proportional to the 40x24 world grid (a size-5 shape occupies 5.0x5.0 world units); vector geometry must scale proportionally to the registered pixel resolution
- (constraint) Network handling reuses fujinet-nio-lib unchanged; no changes to other client targets or build of existing targets may break
- (capability) CAP-1 Amiga target builds and connects: make amiga produces a binary that registers a pixel resolution via fujinet-nio-lib and joins a live Bouncy World server
- (capability) CAP-2 Vector playfield rendering: client converts each embedded shape id to ordered polygon geometry scaled from world units to pixels and renders live world state as filled polygons on a double-buffered fullscreen lowres screen
- (capability) CAP-3 Platform integration shims: keyboard control, delay/timing, screen lifecycle (init/double buffer/shutdown) implemented behind the existing platform headers so shared common code runs unmodified
- (capability) CAP-4 Sound effects: collision/event sounds equivalent to other targets play during gameplay using OS audio APIs available on KS1.3
- (assumption) Assumed NTSC machines get 320x200 and PAL get 320x256; exact status/info presentation (text on playfield vs separate area) left to implementation within 'legible' requirement
